# Release artifact signing

Source Weaver release signing is signing-ready but unsigned by default until release maintainers configure real signing credentials. The release workflow must never fabricate signatures or claim signed artifacts unless the relevant key or certificate was actually used during that run.

## Current status

- Windows Authenticode signing is supported by `scripts/package-windows.ps1` when a code-signing PFX and SignTool are configured.
- Release checksum manifests are generated by `scripts/create-release-checksums.sh` for tag releases.
- OpenPGP detached signatures for `SHA256SUMS` are supported by `scripts/sign-release-checksums.sh` when a release signing key is configured.
- Repository artifacts remain unsigned when the required secrets are absent.
- Signed update metadata is generated only when `SOURCEWEAVER_UPDATE_SIGNING_KEY_BASE64` is configured. The workflow does not publish unsigned update metadata.
- Linux AppImages, Linux tarballs, Windows zip archives, and Windows setup executables remain downloadable without signatures so portable releases continue to work.

## Research notes

Microsoft SignTool documentation checked on 2026-08-07 describes SignTool as the command-line tool for digitally signing files, verifying signatures, removing signatures, and time stamping files. It is distributed with the Windows SDK. Current SignTool documentation also says modern Windows SDK builds require `/fd` for the file digest algorithm and `/td` for the timestamp digest algorithm, and it recommends SHA-256.

GnuPG documentation checked on 2026-08-07 describes detached signatures as a separate signature file created from a private key and verified with the corresponding public key. It documents that both the original document and detached signature are needed for verification, for example `gpg --verify doc.sig doc`.

## Windows Authenticode plan

Windows release signing uses Authenticode through Microsoft SignTool. Source Weaver signs Windows executable payloads before archiving and signs the final NSIS setup executable after `makensis` produces it.

The intended signed files are:

- staged `sourceweaver.exe`;
- staged `sourceweaver-desktop.exe`;
- final `sourceweaver-<version>-windows-x86_64-setup.exe`.

The portable zip contains the signed staged executables when Windows signing is configured before zip creation. The setup executable receives its own Authenticode signature after NSIS packaging.

### Windows signing configuration

`scripts/package-windows.ps1` accepts these signing inputs as parameters or environment variables:

| Purpose | Parameter | Environment variable |
| --- | --- | --- |
| SignTool location | `-SignToolPath` | `SOURCEWEAVER_WINDOWS_SIGNTOOL` or `SIGNTOOL` |
| PFX file path | `-SigningCertificatePfxPath` | `SOURCEWEAVER_WINDOWS_SIGNING_PFX_PATH` |
| Base64-encoded PFX | `-SigningCertificatePfxBase64` | `SOURCEWEAVER_WINDOWS_SIGNING_PFX_BASE64` |
| PFX password | `-SigningCertificatePassword` | `SOURCEWEAVER_WINDOWS_SIGNING_PFX_PASSWORD` |
| RFC 3161 timestamp URL | `-TimestampUrl` | `SOURCEWEAVER_WINDOWS_TIMESTAMP_URL` |
| Require signing | `-RequireSigning` | none |

The GitHub release workflow passes these secrets/variables to the Windows packaging script when present:

- `SOURCEWEAVER_WINDOWS_SIGNING_PFX_BASE64`
- `SOURCEWEAVER_WINDOWS_SIGNING_PFX_PASSWORD`
- `SOURCEWEAVER_WINDOWS_TIMESTAMP_URL`
- `SOURCEWEAVER_WINDOWS_SIGNTOOL`

`-RequireSigning` should be enabled only after the project has a real certificate and a tested recovery path. Until then, missing signing secrets make signing a no-op.

### Windows verification

Release maintainers can verify a signed Windows artifact from PowerShell:

```powershell
Get-AuthenticodeSignature .\sourceweaver-vX.Y.Z-windows-x86_64-setup.exe | Format-List
```

Or with SignTool:

```powershell
signtool verify /pa /v .\sourceweaver-vX.Y.Z-windows-x86_64-setup.exe
```

A signed artifact should have a signer certificate and a successful verification result under the expected policy. Timestamp validation should continue to work after the signing certificate expires, provided the timestamp was produced by a trusted timestamp service while the certificate was valid.

## Linux and cross-platform checksum plan

Linux tarballs and AppImages do not use a native platform trust prompt comparable to Windows Authenticode in this repository. The baseline release integrity mechanism is a `SHA256SUMS` file covering every top-level release artifact and, when configured, an OpenPGP detached signature for that manifest.

Tag releases generate:

```text
SHA256SUMS
SHA256SUMS.asc   # only when SOURCEWEAVER_GPG_PRIVATE_KEY_BASE64 is configured
```

The checksum manifest lets users detect corrupted or tampered downloads. The detached OpenPGP signature lets users verify that the checksum manifest came from the holder of the published release signing key.

### OpenPGP signing configuration

`scripts/sign-release-checksums.sh` uses:

| Purpose | Environment variable |
| --- | --- |
| Base64-encoded private key export | `SOURCEWEAVER_GPG_PRIVATE_KEY_BASE64` |
| Private key passphrase, if needed | `SOURCEWEAVER_GPG_PASSPHRASE` |
| Fail when no key is configured | `SOURCEWEAVER_REQUIRE_RELEASE_SIGNATURES=1` |

The script imports the private key into a temporary `GNUPGHOME`, signs `SHA256SUMS`, verifies the detached signature, and removes the temporary keyring. If no key is configured and signatures are not required, the script prints a skip message and exits successfully.

### Checksum and OpenPGP verification

Download the artifacts, `SHA256SUMS`, and `SHA256SUMS.asc` when present into one directory, then verify checksums:

```bash
sha256sum -c SHA256SUMS
```

Verify the detached signature after importing the published Source Weaver release public key:

```bash
gpg --verify SHA256SUMS.asc SHA256SUMS
```

Both checks matter. `sha256sum -c` verifies artifact bytes against the manifest. `gpg --verify` verifies the manifest against the release signing key.

## Signed update metadata

`sourceweaver update manifest` signs the canonical update-manifest payload with an Ed25519 private key supplied through `SOURCEWEAVER_UPDATE_SIGNING_KEY_BASE64`. The release workflow writes `sourceweaver-update-manifest.json` only when that secret is configured.

The matching Ed25519 public key is not secret. Release maintainers must publish the public key or put it in release notes before asking users to run signed update checks. The desktop and CLI update paths require that public key and refuse unsigned metadata.

The update manifest covers:

- schema version;
- app id;
- channel;
- candidate version;
- publication timestamp;
- release notes URL;
- per-target artifact names, URLs, sizes, and SHA-256 digests.

The manifest signature protects those fields. Artifact bytes are still verified separately by SHA-256 before Source Weaver writes a downloaded artifact.

## Key and certificate ownership

- The repository owner or designated release maintainer owns release-signing decisions.
- Windows code-signing certificates should be issued to the appropriate legal publisher and stored outside the repository.
- OpenPGP release keys should be generated on a maintained, encrypted maintainer machine or hardware-backed token where possible.
- Public verification material, such as the OpenPGP public key fingerprint and certificate publisher name, should be documented in release notes before signatures are required.
- Private keys, PFX files, passphrases, token PINs, and recovery material must never be committed to the repository.

## CI secret storage

GitHub Actions secrets are acceptable for the first automated implementation when the project has no external signing service. Prefer a dedicated signing environment with restricted maintainers and tag-release-only deployment rules.

Recommended GitHub storage:

- Put PFX/private-key material and passwords in GitHub Actions secrets.
- Put non-secret tool paths and timestamp URLs in GitHub Actions variables.
- Restrict signing workflow permissions to release maintainers.
- Enable branch and tag protections before requiring signatures.
- Audit workflow runs that access signing secrets.

Future hardening options include a hardware token, cloud KMS/HSM-backed signing, Azure Trusted Signing, Sigstore keyless signing for checksum attestations, or a dedicated signing service that keeps private keys outside CI runners.

## Rotation and compromise response

Rotate signing credentials when:

- a certificate or key approaches expiration;
- a maintainer with signing access leaves the project;
- a private key, PFX, password, token, or CI secret may have been exposed;
- signing policy changes require a stronger key or certificate.

Rotation steps:

1. Generate or purchase the replacement key/certificate.
2. Add replacement secrets and variables to the restricted signing environment.
3. Run a staging tag or manual release dry run and verify signatures.
4. Publish the new public key fingerprint or certificate publisher details.
5. Remove old secrets after the transition window.
6. Revoke compromised credentials and publish a security notice when compromise is suspected.

## Release checklist additions

For every signed release:

1. Confirm the Windows job shows SignTool signing output for each expected executable.
2. Confirm `SHA256SUMS` exists in the release artifacts.
3. Confirm `SHA256SUMS.asc` exists when OpenPGP signing is configured or required.
4. Download release artifacts and verify `sha256sum -c SHA256SUMS`.
5. Verify `gpg --verify SHA256SUMS.asc SHA256SUMS` when the detached signature exists.
6. Verify Windows Authenticode signatures with `Get-AuthenticodeSignature` or `signtool verify /pa /v` when a certificate was configured.
7. Record which signing credentials were used in the release evidence without exposing secrets.

## Unsigned limitations

Unsigned Windows executables and setup installers may trigger Windows Defender SmartScreen or other reputation prompts. Unsigned Linux artifacts rely on GitHub transport security and checksum verification until an OpenPGP signature is configured. A checksum without a trusted signature detects accidental corruption and mismatched downloads, but it does not prove publisher identity when an attacker can alter both the artifact and checksum file.

Until real signing credentials are configured, release notes and issue evidence must say that signing hooks and checksum generation are implemented, while artifacts from that run are unsigned.
